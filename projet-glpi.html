1. Contexte et objectifs

Hobart (environ 290 collaborateurs) utilise GLPI comme outil de gestion de parc informatique et de support (tickets). La version installée en production, GLPI 10.0.9, n'a jamais été mise à jour depuis sa mise en service. Le projet qui m'a été confié consiste à moderniser cet outil autour de quatre axes :

  • Mise à jour de GLPI vers sa dernière version stable (10.0.9 → 11.0.8) ;
  • Remplacement de l'ancien système d'inventaire (plugin OCS Inventory NG) par l'agent GLPI et l'inventaire natif de GLPI 11 (le plugin GLPI Inventory, d'abord envisagé, s'est révélé inutile) ;
  • Structuration de la CMDB (inventaire des postes, contrats, licences) ;
  • Mise en place de la création automatique de tickets par e-mail.

Ce rapport documente les deux premiers axes : la mise à jour du cœur de GLPI, entièrement testée sur un environnement de test avant toute intervention sur le serveur de production (parties 2 à 7), puis appliquée en production (partie 8) ; et le remplacement de l'inventaire par l'agent GLPI, testé sur une machine virtuelle et sur un poste Windows, puis déployé par GPO (parties 9 à 11). Les axes CMDB et création de tickets par e-mail feront l'objet d'un complément.

2. Méthodologie : un environnement de test avant toute intervention

Par principe de précaution — le serveur de production étant utilisé quotidiennement par l'ensemble des équipes — aucune manipulation n'a été effectuée directement sur le serveur réel. Un collègue a fourni une copie complète de la machine virtuelle de production, exportée au format OVA/OVF (fichiers .ovf, .mf et disques .vmdk), permettant de reconstituer un GLPI strictement identique à la production sur un poste de travail personnel, via VirtualBox.

Lors de l'import, l'option « Générer de nouvelles adresses MAC pour toutes les interfaces réseau » a été activée, afin d'éviter tout conflit avec la véritable VM de production restée active sur le réseau de l'entreprise.

3. Prise en main de l'environnement de test

3.1 Connexion et activation du réseau

Après le premier démarrage, la VM importée s'est présentée avec un hostname glpiv2 sous Debian 12. La carte réseau n'étant pas active par défaut, elle a été activée manuellement (ip link set + dhclient), permettant d'obtenir une adresse IP et un accès réseau fonctionnel.

3.2 Connexion en SSH

Une connexion SSH a ensuite été établie depuis PowerShell afin de travailler plus confortablement qu'en console VirtualBox (copier-coller, redimensionnement de la fenêtre, historique des commandes).

4. Diagnostic préalable à la mise à jour

4.1 Version de départ et configuration personnalisée

La version installée a été confirmée via l'écran « À propos » de GLPI : version 10.0.9, avec une mise à jour vers la 11.0.5 alors proposée par l'éditeur. Après recherche des correctifs de sécurité publiés depuis, la cible a finalement été portée à la 11.0.8, dernière version stable disponible, corrigeant plusieurs failles supplémentaires (détail dans le document séparé « Journal des changements 10.0.9 → 11.0.8 »).

L'inspection du serveur a révélé une configuration non standard : le fichier de connexion à la base de données ne se trouve pas dans le dossier d'installation de GLPI mais dans /etc/glpi/config_db.php, une pratique fréquente consistant à séparer la configuration sensible du code de l'application.

4.2 Sauvegardes avant toute manipulation

Avant toute opération, une sauvegarde complète a été réalisée : export de la base de données (mysqldump) et archivage des dossiers de fichiers et de configuration (tar).

Une sauvegarde complémentaire des dossiers /var/lib/glpi (fichiers) et /var/log/glpi (journaux) a également été réalisée selon le même principe, une fois leur emplacement personnalisé identifié.

4.3 Découverte et analyse du plugin d'inventaire existant

Contrairement à l'hypothèse de départ (plugin FusionInventory), l'inspection du dossier plugins a révélé la présence du plugin OCS Inventory NG.

La vérification de sa version dans le code source (setup.php) a montré une version 1.7.3, prévue pour GLPI 9.5/9.6 — largement obsolète et incompatible avec GLPI 11 (dont les versions compatibles du plugin démarrent à la 2.1.8).

Incident 1 Désinstallation du plugin OCS Inventory NG impossible
Symptôme
En tentant de désinstaller proprement le plugin depuis l'interface GLPI, aucune erreur n'apparaît mais l'action reste sans effet : le plugin réapparaît à l'identique après rechargement de la page.
Diagnostic
Surveillance des journaux Apache en temps réel (tail -f /var/log/apache2/error.log) pendant une nouvelle tentative, révélant l'erreur « Unknown database 'ocsweb' » — le plugin tente de nettoyer ses propres tables dans une base de données qui n'a pas été incluse dans l'export de la VM.
Décision
Ce point n'étant pas bloquant pour l'objectif principal (la mise à jour du cœur de GLPI), sa résolution a été reportée à l'axe « inventaire » du projet (remplacement de l'ancien plugin par l'agent GLPI), l'inventaire natif de GLPI 11 ne dépendant plus de ce plugin.

5. Téléchargement et préparation de GLPI 11.0.8

5.1 Vérification de l'accès réseau de la VM

5.2 Incident réseau : bascule du mode Bridged vers NAT

La première tentative de téléchargement de l'archive GLPI 11.0.8 (92 Mo) a affiché un temps estimé de plus de 3 heures, pour un débit mesuré à environ 6-7 Ko/s alors que le PC hôte téléchargeait le même fichier de test instantanément.

Incident 2 Débit réseau très faible en carte réseau « Accès par pont » (Bridged)
Cause probable
Le réseau de l'entreprise applique une limitation ou un filtrage sur le trafic d'une machine virtuelle disposant de sa propre adresse MAC, non reconnue par les équipements réseau.
Solution
Bascule de la configuration réseau de la VM en mode NAT, avec mise en place de règles de redirection de ports (SSH sur le port 2222, puis HTTP sur le port 8080) pour conserver un accès confortable depuis le PC hôte.

5.3 Téléchargement et extraction de l'archive

Une fois le mode NAT en place, le téléchargement s'est effectué à une vitesse normale (environ 18-19 Mo/s), confirmant que le mode réseau était bien à l'origine du ralentissement.

6. Bascule vers la nouvelle version

6.1 Préservation de la configuration personnalisée

Le fichier inc/downstream.php identifié en phase de diagnostic a été recopié dans l'archive nouvellement extraite, afin que GLPI 11 continue de pointer vers les dossiers de configuration personnalisés (/etc/glpi, /var/lib/glpi, /var/log/glpi) sans perte de données.

6.2 Remplacement des fichiers

Le remplacement a été effectué en conservant un filet de sécurité : plutôt que de supprimer l'ancienne installation, celle-ci a été renommée (glpi-old-10.0.9), permettant un retour arrière immédiat en cas de problème. Les droits du nouveau dossier ont ensuite été attribués à l'utilisateur du serveur web (www-data).

6.3 Incident : changement de structure du webroot en GLPI 11

Incident 3 « The web server seems to be misconfigured »
Symptôme
Au premier accès à l'interface après remplacement des fichiers, GLPI affiche une erreur indiquant que la racine web doit correspondre au sous-dossier /public de l'installation.
Cause
Contrairement à GLPI 10 où la racine du serveur web pointait directement sur le dossier d'installation, GLPI 11 impose que le DocumentRoot Apache pointe vers le sous-dossier glpi/public, avec une règle de réécriture d'URL vers public/index.php.
Solution
Modification du fichier de VirtualHost Apache concerné (DocumentRoot + bloc <Directory> avec RewriteEngine), suivie d'un test de configuration (apache2ctl configtest) et d'un redémarrage du service.

7. Migration de la base de données

7.1 Vérification des prérequis

L'assistant de mise à jour de GLPI a ensuite vérifié l'ensemble des prérequis serveur.

Incident 4 Blocage sur les prérequis : extension PHP bcmath absente
Cause
L'extension PHP bcmath (requise pour la gestion des QR codes en GLPI 11) n'est pas installée par défaut sur Debian 12, alors qu'elle est devenue obligatoire.
Solution
Installation via le gestionnaire de paquets (apt install php8.2-bcmath), après quoi l'ensemble des prérequis obligatoires est passé au vert.

7.2 Exécution de la migration

La migration de la base de données a ensuite été lancée. GLPI a exécuté automatiquement l'ensemble des migrations intermédiaires nécessaires (versions 10.0.10 à 10.0.25 puis 11.0.x), sans qu'aucune intervention manuelle ne soit requise.

7.3 Résultat et vérifications finales

Une fois la migration terminée, la connexion à l'interface a été testée avec succès : le tableau de bord affiche l'ensemble des données historiques (tickets, statistiques) sans perte, confirmant l'intégrité des données après la migration.

Un message d'information signale que certains formulaires proviennent du plugin Formcreator, désormais intégré au cœur de GLPI 11 : leur migration vers le nouveau système intégré (commande php bin/console migration:formcreator_plugin_to_core) sera traitée dans un axe ultérieur du projet, cette opération n'étant pas bloquante.

8. Mise en production

Après validation de la procédure par le maître d'apprentissage, la mise à jour a été appliquée sur le serveur de production (172.17.8.60), en suivant à l'identique les étapes validées sur l'environnement de test : sauvegarde de la base et des fichiers, recopie de inc/downstream.php et de la configuration personnalisée, remplacement du dossier en conservant l'ancienne version (glpi-old-10.0.9), DocumentRoot Apache pointant vers glpi/public, installation de l'extension php8.2-bcmath, puis migration de la base de données. Une procédure détaillée, rédigée à partir des résultats du test, a servi de guide (document séparé « Procédure de mise à jour en production »).

Grâce à la phase de test, les deux principaux blocages (webroot /public et extension bcmath) étaient connus à l'avance et ont été traités en quelques minutes. Deux difficultés propres à la production ont en revanche été rencontrées :

  • l'installation de php8.2-bcmath a d'abord échoué (liste de paquets apt obsolète, commande mal collée dans le terminal) ; la solution a été de lancer apt update seul, puis de relancer l'installation ;
  • une erreur TooManyResultsException à la connexion, causée par deux lignes pour un même utilisateur dans la table glpi_users (même anomalie que celle déjà rencontrée sur la machine virtuelle) : voir la partie 12.

La version 11.0.8 est ensuite devenue la version active en production, avec conservation de l'historique des tickets et des données de parc.

9. Agent GLPI : premier test sur la machine virtuelle (Linux)

9.1 Choix de l'inventaire natif plutôt que du plugin GLPI Inventory

Le projet prévoyait au départ le plugin GLPI Inventory pour remplacer l'ancien plugin OCS Inventory NG. L'analyse de GLPI 11 a montré que cette étape était inutile : GLPI intègre désormais un inventaire natif (point d'entrée /front/inventory.php) capable de recevoir directement les inventaires envoyés par l'agent GLPI. Le plugin GLPI Inventory n'apporte que des fonctions avancées (découverte réseau SNMP, déploiement de logiciels, Wake-on-LAN) dont l'entreprise n'a pas besoin ici. Le parc sera donc inventorié par l'agent GLPI seul, ce qui réduit le nombre de composants à maintenir.

Avant d'installer l'agent, il faut vérifier que l'inventaire est bien activé dans GLPI (Administration > Inventaire) : la case « Activer l'inventaire » est cochée, l'authentification des agents est sur « Aucun » et la fréquence d'inventaire est de 24 heures.

9.2 Téléchargement et installation de l'agent

L'agent GLPI 1.19 a été téléchargé depuis le dépôt officiel GitHub du projet (paquet .deb pour Debian) directement sur la machine virtuelle, puis installé avec apt.

Lors de l'installation, apt affiche un avertissement sans gravité :

N: Le téléchargement est effectué en dehors du bac à sable en tant que « root » car le fichier
« /home/glpiv2/glpi-agent_1.19-1_all.deb » n'est pas accessible par l'utilisateur « _apt ».

Il signifie simplement que le fichier se trouve dans le dossier personnel d'un utilisateur, auquel le compte système _apt n'a pas accès. L'installation se déroule normalement ; pour éviter ce message, il suffit de placer le paquet dans /tmp avant de l'installer.

9.3 Configuration et démarrage du service

L'adresse du serveur est définie dans le fichier de configuration de l'agent (/etc/glpi-agent/agent.cfg), via la directive server. Dans ce test, GLPI se trouvant sur la même machine, elle pointe vers http://localhost/front/inventory.php.

Après un redémarrage, le service glpi-agent est actif. Les journaux indiquent que son mini serveur web écoute sur le port 62354 et que la prochaine exécution est planifiée vers l'adresse configurée.

9.4 Premier inventaire

Un inventaire a été forcé immédiatement avec la commande glpi-agent --server … --force. Les messages montrent le dialogue complet avec le serveur : requête « prolog », réponse du serveur confirmant qu'il supporte le protocole de l'agent GLPI, puis exécution de la tâche Inventory et création d'un nouvel inventaire.

Côté GLPI, l'agent apparaît dans Administration > Inventaire > Agents (version 1.19-1), et la machine est créée dans Parc > Ordinateurs avec son système d'exploitation, son processeur et ses logiciels.

10. Agent GLPI sur poste Windows

10.1 Téléchargement et première installation

L'agent Windows se distribue sous forme de paquet MSI (GLPI-Agent-1.19-x64.msi), téléchargé depuis la page officielle des versions du projet.

Une première installation manuelle a été faite sur le poste de travail de l'auteur du rapport, avec l'assistant graphique, en pointant vers le GLPI de la machine virtuelle (redirection de port 127.0.0.1:8080). Le service glpi-agent démarre, un inventaire est forcé avec glpi-agent.bat --force, et le poste apparaît dans le GLPI de test.

10.2 Vérification de l'adresse d'inventaire du vrai GLPI

Avant d'envoyer des inventaires vers le serveur de production, son adresse d'inventaire a été vérifiée depuis un navigateur : http://172.17.8.60/glpi/front/inventory.php. La page répond par une erreur HTTP 405 (méthode non autorisée). C'est le résultat attendu : ce point d'entrée n'accepte que les envois (méthode POST) faits par les agents, et refuse une simple consultation. Une erreur 404 aurait au contraire indiqué une mauvaise adresse.

10.3 Script PowerShell d'installation

Pour industrialiser l'installation sur plusieurs postes, un script PowerShell (Install-GLPIAgent.ps1, fourni en annexe) a été écrit. Il reprend la commande msiexec et y ajoute des vérifications et un journal. Ses étapes sont les suivantes :

  • vérification que le script est lancé en administrateur ;
  • détection d'un agent déjà installé (lecture de la version dans le registre) ;
  • contrôle de la présence du fichier MSI et test de joignabilité du serveur GLPI ;
  • installation silencieuse avec les paramètres du serveur, et journal d'installation ;
  • imposition de l'adresse du serveur dans le registre, redémarrage du service glpi-agent, envoi d'un inventaire immédiat ;
  • affichage de la fin du journal de l'agent et écriture d'un journal du script (C:\Windows\Temp\GLPI-Agent-install.log).

Les paramètres de l'installation silencieuse sont les suivants :

ParamètreRôle
/quietinstallation sans fenêtre ni question à l'utilisateur
SERVER=adresse du serveur GLPI qui reçoit les inventaires
TAG=étiquette affichée sur la fiche de l'ordinateur (utilisée pour le test, abandonnée ensuite)
EXECMODE=1installe l'agent comme service Windows (c'est le mode par défaut)
RUNNOW=1envoie un premier inventaire dès la fin de l'installation
ADD_FIREWALL_EXCEPTION=1ajoute une exception dans le pare-feu Windows pour l'agent (le pare-feu n'est pas désactivé)

Exécuté sur le poste de test, le script détecte l'agent déjà installé, vérifie le serveur, installe, démarre le service et envoie l'inventaire, en affichant chaque étape en couleur.

En amont, la tentative de passer la stratégie d'exécution en « Bypass » (Set-ExecutionPolicy) a produit un message d'erreur sans gravité : sur les postes de l'entreprise, la stratégie est déjà définie à « Unrestricted » par GPO, et ce paramètre prime sur celui de la session. Le script peut donc être lancé directement.

10.4 Incident : le poste n'apparaît pas dans le vrai GLPI

Incident 5 L'inventaire est « envoyé » mais le poste reste absent du GLPI de production
Symptôme
Le script indiquait « Inventaire envoyé » et le service tournait, mais le poste n'apparaissait pas dans Parc > Ordinateurs du serveur de production.
Diagnostic
La clé de registre HKLM:\SOFTWARE\GLPI-Agent contenait encore server = http://127.0.0.1:8080/front/inventory.php, l'adresse de la machine virtuelle utilisée lors de la première installation. Le journal de l'agent confirmait l'erreur : « Can't connect to 127.0.0.1:8080 (connexion refusée) ». Une réinstallation du MSI conserve en effet la configuration existante dans le registre : l'adresse passée en paramètre n'était donc pas appliquée.
Solution
Écrire explicitement l'adresse du vrai serveur dans le registre (Set-ItemProperty), redémarrer le service puis forcer un inventaire. Le script a été complété pour réaliser lui-même ces trois actions, et afficher la fin du journal de l'agent pour vérification.

Ce problème ne concernait que le poste de test, où un agent avait déjà été installé avec l'adresse de la machine virtuelle. Pour les autres postes, l'agent est installé pour la première fois avec la bonne adresse : la protection n'est donc pas nécessaire dans la commande de déploiement.

10.5 Version simplifiée en une seule ligne

Le maître d'apprentissage a proposé une version réduite à une seule commande msiexec, qui reprend l'essentiel (serveur, service, exception pare-feu). Une commande équivalente, pour un poste sans agent, est la suivante : 

msiexec /i "GLPI-Agent-1.19-x64.msi" /quiet SERVER=http://172.17.8.60/glpi/front/inventory.php EXECMODE=1 RUNNOW=1 ADD_FIREWALL_EXCEPTION=1

Cette ligne remplace le script lorsque le poste n'a pas déjà un agent. Le script reste utile pour ce que la ligne ne fait pas : contrôle du serveur, journal, correction d'une ancienne configuration. C'est la commande msiexec (sans le script) qui a été retenue pour le déploiement par GPO.

11. Déploiement par GPO

11.1 Contrainte et principe

L'agent doit être installé automatiquement sur tous les postes, mais les techniciens lancent le VPN après avoir déverrouillé leur session : une installation déclenchée à l'ouverture de session ou au démarrage pourrait échouer, faute d'accès au partage réseau. Le déploiement repose donc sur une tâche planifiée immédiate définie dans la configuration de l'ordinateur (préférences de stratégie de groupe), exécutée par le compte système dès que la stratégie est appliquée, avec des relances en cas d'échec.

11.2 Partage réseau du paquet

Le paquet MSI de l'agent (version 1.21, la plus récente au moment du déploiement) est placé dans un dossier GLPIAgent sur un partage du serveur de fichiers. Ce partage doit être lisible par les comptes ordinateurs du domaine, puisque la tâche s'exécute avec le compte système de chaque poste. Un chemin réseau (UNC) est indispensable : un poste ne peut pas installer un MSI situé sur le disque d'un autre.

11.3 La tâche planifiée « GLPI AGENT install »

La GPO « GLPI Agent Install Scheduled Task » est rattachée aux ordinateurs. Elle crée une tâche immédiate qui lance msiexec.exe avec les arguments ci-dessous ; la tâche s'exécute en NT AUTHORITY\System avec les autorisations maximales, donc sans dépendre d'un utilisateur connecté.

La ligne de commande exécutée est :

msiexec.exe /quiet /i \\172.17.8.22\ocs$\GLPIAgent\GLPI-Agent-1.21-x64.msi ADD_FIREWALL_EXCEPTION=1 DEBUG=2 NO_HTTPD=1 SERVER=http://172.17.8.60/glpi RUNNOW=1
ÉlémentRôle
/quiet /i <chemin UNC>installation silencieuse du MSI situé sur le partage réseau
ADD_FIREWALL_EXCEPTION=1ajoute l'exception pare-feu de l'agent
DEBUG=2journal très détaillé : utile pendant le déploiement pour diagnostiquer un poste, à retirer ensuite (le journal est limité à 4 Mo)
NO_HTTPD=1désactive le mini serveur web de l'agent (port 62354) : aucun port n'est ouvert sur les postes ; en contrepartie, GLPI ne peut pas demander un inventaire à la demande, l'agent envoie ses inventaires de lui-même
SERVER=http://172.17.8.60/glpiadresse du serveur GLPI de production
RUNNOW=1premier inventaire dès la fin de l'installation

Les options de la tâche répondent à la contrainte du VPN : si l'installation échoue (partage injoignable, par exemple), elle est relancée toutes les heures, jusqu'à 3 fois ; si un démarrage planifié est manqué, elle s'exécute dès que possible ; elle ne dépend pas du fait que l'ordinateur soit branché sur le secteur (utile pour les portables) ; et si elle est déjà en cours, la nouvelle exécution est ignorée (règle « IgnoreNew »).

11.4 Condition d'application : ne pas réinstaller à chaque actualisation

Une tâche immédiate peut être réappliquée à chaque actualisation de la stratégie. Pour éviter de réinstaller l'agent sur les postes qui l'ont déjà, l'élément est soumis à un ciblage au niveau de l'élément : une correspondance de registre de type « clé existante » sur HKEY_LOCAL_MACHINE\SOFTWARE\GLPI-Agent, avec l'option « non » (opérateur NOT). La tâche ne s'exécute donc que si la clé GLPI-Agent n'existe pas encore, c'est-à-dire sur un poste sans agent. L'option « Appliquer une fois et ne pas réappliquer » est sur « Non » : la condition de registre suffit.

Conséquence à connaître : un poste qui possède déjà une clé GLPI-Agent (par exemple le poste de test, installé avec l'adresse de la machine virtuelle) n'est jamais reconfiguré par cette GPO. Il faudrait le corriger manuellement, comme décrit en partie 10.4.

11.5 Déploiement et résultat

Le déploiement a d'abord été validé sur une agence. Le test s'étant bien déroulé, la GPO a ensuite été étendue à l'ensemble du parc. Dès le lendemain matin (16 octobre 2026), la liste Parc > Ordinateurs de GLPI affichait 223 ordinateurs (avec le filtre par modèle actif sur cette vue), dont les dernières modifications datent du 15 au 16 octobre : les postes envoient leur inventaire automatiquement après installation de l'agent.

Quelques points restent à surveiller : un poste dont la première remontée est incomplète (par exemple sans système d'exploitation affiché) sera complété par l'inventaire suivant ; les postes éteints ou hors réseau recevront l'agent à leur prochaine connexion ; et le paramètre DEBUG=2 pourra être retiré une fois le déploiement stabilisé.

12. Synthèse des incidents rencontrés et résolus

Les tests et le déploiement ont permis d'identifier et de résoudre neuf incidents ou points d'attention. Les quatre premiers ont été traités sur l'environnement de test, avant toute intervention sur la production, ce qui constitue l'un des principaux apports de cette phase :

Annexe — Script PowerShell d'installation de l'agent

Script utilisé pour le test sur poste Windows (partie 10.3). Les accents ont été retirés des messages pour éviter tout problème d'encodage dans la console. 

$GlpiServer = "http://172.17.8.60/glpi/front/inventory.php"
$MsiName    = "GLPI-Agent-1.19-x64.msi"
$Tag        = "TEST-AGENT"
$Reg = "HKLM:\SOFTWARE\GLPI-Agent"
$Dir = "C:\Program Files\GLPI-Agent"

function Log($m, $c = "White") {
    $l = "$(Get-Date -f 'yyyy-MM-dd HH:mm:ss')  $m"
    Write-Host $l -ForegroundColor $c
    Add-Content "C:\Windows\Temp\GLPI-Agent-install.log" $l
}

if (-not ([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)) {
    Write-Host "Lancer ce script dans un PowerShell administrateur." -ForegroundColor Red
    exit 1
}

Log "===== Debut installation agent GLPI sur $env:COMPUTERNAME =====" Cyan

$v = (Get-ItemProperty "$Reg\Installer" -ErrorAction SilentlyContinue).Version
if ($v) { Log "Agent deja installe (version $v), il sera reconfigure." Yellow }

$Msi = Join-Path $PSScriptRoot $MsiName
if (-not (Test-Path $Msi)) { Log "MSI introuvable : $Msi" Red; exit 1 }

if (Test-Connection ([Uri]$GlpiServer).Host -Count 1 -Quiet) {
    Log "Serveur GLPI joignable." Green
} else {
    Log "Serveur GLPI injoignable, inventaire envoye plus tard." Yellow
}

$p = Start-Process msiexec.exe -Wait -PassThru -ArgumentList "/i `"$Msi`" /quiet SERVER=`"$GlpiServer`" TAG=`"$Tag`" EXECMODE=1 RUNNOW=1 ADD_FIREWALL_EXCEPTION=1 /l*v C:\Windows\Temp\GLPI-Agent-msi.log"
if ($p.ExitCode -notin 0, 3010) { Log "Echec de l'installation (code $($p.ExitCode))." Red; exit $p.ExitCode }
Log "Installation terminee (code $($p.ExitCode))." Green

Set-ItemProperty $Reg -Name server -Value $GlpiServer
Set-ItemProperty $Reg -Name tag -Value $Tag
Log "Serveur configure : $((Get-ItemProperty $Reg).server)" Green

Restart-Service glpi-agent; Start-Sleep 5
if ((Get-Service glpi-agent).Status -eq "Running") { Log "Service glpi-agent demarre." Green } else { Log "Service glpi-agent arrete." Red }

Log "Envoi d'un inventaire immediat..."
& "$Dir\glpi-agent.bat" --force | Out-Null
Get-Content "$Dir\logs\glpi-agent.log" -Tail 10 | ForEach-Object { Log "   $_" }

Log "===== Fin. Verifier le PC dans GLPI : Parc > Ordinateurs =====" Cyan
